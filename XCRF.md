# SAP CPI – CSRF Token Handling: Complete Notes & Use Cases

-----

## 1. What is CSRF?

**Cross-Site Request Forgery (CSRF)** is a type of web security attack where a malicious actor tricks an authenticated user’s browser into submitting an unauthorized HTTP request to a trusted site or service — exploiting the trust the server has in the user’s session.

In the SAP CPI (Cloud Platform Integration / Cloud Integration) context, CSRF protection is used to validate that modifying HTTP requests (POST, PUT, PATCH, DELETE) genuinely originate from the authorized caller and not from a forged cross-site request.

-----

## 2. Core Concept: The CSRF Token Flow

The CSRF protection mechanism in SAP CPI follows a **two-step pattern**:

```
Step 1: Fetch Token
  Caller → sends GET or HEAD request
          with header:  X-CSRF-Token: Fetch
          to the iFlow endpoint
  CPI   → responds with the CSRF token
          in header:    X-CSRF-Token: <token_value>

Step 2: Use Token for Modifying Request
  Caller → sends POST / PUT / PATCH / DELETE
          with header:  X-CSRF-Token: <token_value>
  CPI   → validates the token → processes the request
```

> **Key Rule:** CSRF tokens are **NOT required** for non-modifying requests: `GET`, `HEAD`, `OPTIONS`.  
> They ARE required for modifying requests: `POST`, `PUT`, `PATCH`, `DELETE`.

-----

## 3. CSRF in Inbound HTTPS (CPI as Server)

### 3.1 Overview

SAP CPI natively supports CSRF protection for **inbound HTTPS connections** via the HTTPS Sender Adapter. This is a built-in, out-of-the-box feature — no custom coding is required to enable it.

### 3.2 Enabling CSRF Protection

In the HTTPS Sender Adapter configuration:

- Navigate to the **Connection** tab
- Check the **CSRF Protection** checkbox

Once enabled, CPI will:

- Accept `X-CSRF-Token: Fetch` requests (GET/HEAD) and return a token
- Validate the `X-CSRF-Token` header on incoming modifying requests
- Reject modifying requests **without** a valid token with HTTP `403 Forbidden`

### 3.3 Token Scope and Validity

- CSRF tokens generated by CPI are **valid within the scope of the session** in which they were obtained
- Tokens are tied to the **iFlow-specific endpoint**, NOT a global/tenant-wide endpoint
- Each iFlow that exposes a CSRF-protected endpoint issues its **own token**

> ⚠️ **Important Note:** CSRF tokens obtained from one iFlow endpoint **cannot** be reused for a different iFlow endpoint.

### 3.4 Routing CSRF Fetch Requests in an iFlow

A best practice is to add a **Router step** inside the iFlow to separate the CSRF token-fetch flow from the main business logic:

```
Incoming Request
     │
     ▼
  [Router]
     ├─── if X-CSRF-Token = Fetch ──→ [End / Return 200 with token]
     │
     └─── else (POST/PUT/PATCH)  ──→ [Main Business Process Flow]
```

This ensures that:

- Token-fetch requests don’t inadvertently trigger business logic
- The flow is clean and clearly separated

### 3.5 Behavior for Non-Modifying Requests

> CSRF protection **only applies to modifying requests**. Even if CSRF Protection is enabled on the adapter, CPI will **not** reject `GET`, `HEAD`, or `OPTIONS` requests that arrive without a CSRF token. This is by design.

### 3.6 Multi-Node Tenant Issue (Intermittent 403)

On CPI tenants with **more than one worker node**, an intermittent `missing CSRF token` error can occur. This happens because:

- The token is fetched from Node A
- The subsequent POST is routed to Node B
- Node B does not recognize the token from Node A

**Workaround:** Ensure sticky session / session affinity is configured, or consult SAP KBA 3512805.

## 4. CSRF in Outbound HTTP Adapter (CPI as Client — On-Premises)

### 4.1 Overview

When CPI calls an **on-premises SAP system** (e.g., SAP ECC, S/4HANA) via the **HTTP Receiver Adapter**, CSRF token handling must be done **manually** inside the iFlow. This is different from the OData adapter which handles it implicitly.

### 4.2 Step-by-Step iFlow Design

```
[Start]
   │
   ▼
[HTTP Receiver — HEAD Request]
   Address: /sap/opu/odata/...
   Method: HEAD
   Request Header:  X-CSRF-Token: Fetch
   Response Header: * (all headers captured)
   │
   ▼
[Content Modifier]
   Exchange Property: set-cookie → cookie
   Message Header:    Content-Type = application/json
   Body:              <actual POST payload>
   │
   ▼
[Groovy Script]
   Ensure cookie header values are delimited with ';'
   │
   ▼
[HTTP Receiver — POST Request]
   Method: POST
   Headers: X-CSRF-Token (from HEAD response), cookie (modified)
   │
   ▼
[End]
```

### 4.3 Why Session Continuity Matters

The CSRF token returned by the backend is **only valid when used within the same HTTP session**. The session is tracked via the `set-cookie` header returned in the HEAD response.

> **Critical:** The `set-cookie` header from the HEAD call must be converted to `cookie` for use in the POST call. If this transformation is skipped, the backend will reject the POST with `403`.

### 4.4 HTTP Session Reuse Configuration

To ensure the HEAD and POST calls share the same HTTP session, configure the iFlow’s **Runtime Configuration**:

|Setting           |Value          |
|------------------|---------------|
|HTTP Session Reuse|**On Exchange**|

This setting is found under:  
`Integration Flow → Runtime Configuration → HTTP Session Reuse`

Options available:

- `None` — No session reuse (default)
- `On Exchange` — Reuse within a single message exchange
- `On Integration Flow` — Reuse across multiple exchanges (good for frequent calls)

> ⚠️ **Note:** Without `On Exchange`, the HEAD and POST will use different sessions, making the token invalid.

### 4.5 Request/Response Header Configuration

In the HTTP Receiver Adapter (HEAD call):

- **Request Header:** `*` (send all headers including `X-CSRF-Token: Fetch`)
- **Response Header:** `*` (capture all response headers including `X-CSRF-Token` and `set-cookie`)

## 5. CSRF with OData Receiver Adapter (Outbound)

### 5.1 Implicit Handling

When using the **OData V2 Receiver Adapter**, CSRF token management is handled **automatically** by the adapter. No manual steps are needed.

- The OData adapter performs an implicit GET/HEAD for the token
- Then performs the actual modifying call with the token attached

> ✅ **You do NOT need to manually configure CSRF token steps when using the OData adapter.**

### 5.2 CSRF Protected Flag

In the OData adapter’s **Connection** properties, there is a checkbox: **CSRF Protected**

- **Enabled:** The adapter makes 2 HTTP calls per operation — one to fetch the token, one for the actual call
- **Disabled:** Skips the token-fetch call; use only if the target service does NOT require CSRF

### 5.3 OData Token Reuse (Performance Optimization)

In scenarios with multiple OData calls (e.g., GET to check existence → POST to create), the OData adapter can **reuse the token** from the first call:

**Setup:**

1. First call (GET) — CSRF Protected: **Enabled**  
   → Fetches and stores the CSRF token
1. Second call (POST) — CSRF Protected: **Disabled**  
   → Reuses the token from the GET call session

**Prerequisite:**  
`HTTP Session Reuse = On Exchange` must be set in the Integration Flow’s Runtime Configuration.

**Result:** Eliminates the extra token-fetch HTTP call, reducing backend round-trips.

## 6. Handling CSRF Tokens in CPI — General Notes

|Topic                     |Details                                                  |
|--------------------------|---------------------------------------------------------|
|Token Header Name         |`X-CSRF-Token`                                           |
|Fetch Request Header Value|`X-CSRF-Token: Fetch`                                    |
|Token Source              |Response header from target endpoint                     |
|Token Usage               |Passed in header of modifying request                    |
|Session Binding           |Token is tied to HTTP session (cookie)                   |
|Required For              |POST, PUT, PATCH, DELETE                                 |
|Not Required For          |GET, HEAD, OPTIONS                                       |
|Inbound Adapter           |HTTPS Sender Adapter (checkbox to enable)                |
|Outbound Adapter          |HTTP Receiver Adapter (manual), OData Adapter (automatic)|

## 7. Use Cases

-----

### Use Case 1: Third-Party App Posting Data to CPI (Inbound)

**Scenario:**  
A third-party web application (e.g., a customer portal) needs to POST order data to a CPI iFlow via HTTPS.

**Solution:**

1. CPI iFlow exposes an HTTPS endpoint with **CSRF Protection enabled**
1. The third-party app:
- Sends a `GET` with `X-CSRF-Token: Fetch`
- Receives a token in the response
- Stores the token (and session cookie)
- Posts the order payload with `X-CSRF-Token: <value>`
1. CPI validates the token and processes the order

**In Postman (Testing):**

- Use environment variables to auto-capture the token from Step 1’s response
- Inject the variable into Step 2’s header automatically using a **Postman Test Script**

-----

### Use Case 2: CPI Posting to On-Premises SAP ECC via HTTP Adapter

**Scenario:**  
CPI needs to insert a sales order into an on-premises SAP ECC system using an OData POST call. The ECC system is connected via SAP Cloud Connector.

**Solution:**

1. iFlow sends an HTTP HEAD request with `X-CSRF-Token: Fetch` to the ECC OData endpoint (via Cloud Connector virtual host/port)
1. CPI stores the returned `X-CSRF-Token` value and `set-cookie`
1. Content Modifier converts `set-cookie` → `cookie`
1. Groovy script formats cookie values with `;` delimiter
1. iFlow sends POST with the token and cookie
1. `HTTP Session Reuse = On Exchange` ensures both calls share the same session

**Critical Config:**

- Cloud Connector virtual host and port used as target address
- `Request Header: *` and `Response Header: *` in the HEAD adapter

-----

### Use Case 3: CPI Calling S/4HANA Public Cloud OData API

**Scenario:**  
CPI needs to submit timesheet data to SAP S/4HANA Public Cloud using `API_MANAGE_WORKFORCE_TIMESHEET`.

**Common Problem:** HTTP 403 Forbidden even with correct CSRF token.

**Root Cause:** `HTTP Session Reuse` was set to `None` (default).

**Fix:**

- Change Runtime Configuration → `HTTP Session Reuse = On Integration Flow`
- Ensure the Communication User has the correct roles in S/4HANA

-----

### Use Case 4: CPI with Multiple OData Calls — Token Reuse Optimization

**Scenario:**  
CPI integration checks if a customer exists in SAP Marketing Cloud (GET), then creates it if not found (POST). Avoiding double CSRF token fetches is critical for performance.

**Solution:**

1. GET call → `CSRF Protected: Enabled`  
   → Token is fetched and stored in session
1. POST call → `CSRF Protected: Disabled`  
   → Token from GET is reused automatically

**Prerequisite:** `HTTP Session Reuse = On Exchange`

**Benefit:** Eliminates one HTTP round-trip per record, significantly improving performance in mass data loads.

-----

### Use Case 5: Node.js App Calling CPI iFlow (OAuth + CSRF)

**Scenario:**  
A Node.js application on SAP BTP needs to call a CPI iFlow endpoint that is CSRF-protected and uses OAuth authentication.

**Flow:**

1. App fetches JWT access token from XSUAA
1. App sends GET to iFlow with:
- `Authorization: Bearer <JWT>`
- `X-CSRF-Token: Fetch`
1. CPI returns CSRF token
1. App sends POST with:
- `Authorization: Bearer <JWT>`
- `X-CSRF-Token: <value>`
- Payload body

**Notes:**

- The iFlow HTTPS adapter must have `CSRF Protection: Enabled`
- Authorization must be set to `User Role` with the appropriate role assigned

-----

### Use Case 6: SOAP/HTTP Sender Bypassing CSRF for Read-Only APIs

**Scenario:**  
An external system sends frequent GET requests to a CPI iFlow to poll for status data. CSRF is technically enabled on the adapter.

**Behavior:**  
CPI will NOT enforce CSRF for GET requests, even if the checkbox is enabled. The caller does not need to fetch a token.

**Takeaway:**  
No extra handling needed for read-only GET integrations — CSRF enforcement is purely for modifying HTTP methods.

## 8. Common Errors & Troubleshooting

|Error                                         |Cause                                        |Fix                                                          |
|----------------------------------------------|---------------------------------------------|-------------------------------------------------------------|
|`HTTP 403 – CSRF token validation failed`     |Token missing or invalid in modifying request|Fetch token first; pass it in `X-CSRF-Token` header          |
|`HTTP 403 – Intermittent on multi-node tenant`|Token from Node A used on Node B             |Configure sticky session or see SAP KBA 3512805              |
|`HTTP 403 – Token valid but POST still fails` |Session cookie not passed correctly          |Convert `set-cookie` → `cookie`; ensure session reuse        |
|`HTTP 403 – S/4HANA Public Cloud`             |HTTP Session Reuse = None                    |Set to `On Exchange` or `On Integration Flow`                |
|`HTTP 500 in CPI caller iFlow`                |CPI could not pass CSRF token to target      |Check Request Header config is `*`; check session reuse      |
|Token not appearing in response               |Request Header not set to `*`                |Set both Request Header and Response Header to `*` in adapter|

## 9. Key Configuration Summary

### Inbound CSRF (CPI as Server)

```
HTTPS Sender Adapter → Connection Tab
  ✅ CSRF Protection: [checked]
iFlow → Add Router to separate token-fetch from business logic
```

### Outbound CSRF via HTTP Adapter (CPI as Client)

```
Runtime Configuration:
  HTTP Session Reuse: On Exchange

Step 1 — HTTP HEAD Adapter:
  Method: HEAD
  Request Header: *
  Response Header: *
  Header: X-CSRF-Token = Fetch

Step 2 — Content Modifier:
  Exchange Property: set-cookie → cookie
  
Step 3 — Groovy Script:
  Format cookie with ';' delimiter

Step 4 — HTTP POST Adapter:
  Method: POST
  Headers: X-CSRF-Token, cookie
```

### Outbound CSRF via OData Adapter

```
OData Adapter → Connection:
  CSRF Protected: [checked]   ← for standalone calls
  CSRF Protected: [unchecked] ← when reusing token from prior GET

Runtime Configuration:
  HTTP Session Reuse: On Exchange  ← required for token reuse
```
